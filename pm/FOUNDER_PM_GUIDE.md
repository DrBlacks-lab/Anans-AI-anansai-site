# ANANS Village — Founder PM Operating Guide

Status: ACTIVE PROJECT CONTROL DOCUMENT
Scope: `anansai.org` / ANANS Village restricted-preview build
Working branch: `aspeak/anans-village-preview-auth-v1`

## Founder role

The Founder controls purpose, consequential authority, resource ceilings, public claim ceilings, trade-secret disclosure, irreversible external effects, and final promotion/release decisions.

The Founder should not manage ordinary implementation repair once a bounded mandate has been issued. PM owns decomposition, sequencing, duplicate-surface reconciliation, technical repair, test reruns, AEL candidate management, RevLane checkpoints, Track X prioritization, evidence collection, and terminal reporting inside the authorized preview envelope.

PM is not governance authority. Planning, recommendation, successful tests, deployment health, or model confidence do not create new consequential permission.

## Current project objective

Build ANANS Village as a human-readable civic ontology over actual ANANS primitives, tools, roles, authority boundaries, evidence, and backend functions.

The visitor-facing semantic chain is:

`RECOGNIZABLE BUILDING -> HUMAN FUNCTION -> ANANS PRIMITIVE -> TOOL/SERVICE -> BACKEND FUNCTION -> AUTHORITY CHECK -> RECEIPT/STATUS`

The Village must not become a parallel ANANS implementation. It should project canonical primitives and existing services wherever available; missing functions remain explicitly `SPECIFIED_NOT_BUILT`, `EXPERIMENTAL`, `WITHHELD_BY_AUTHORITY`, or `UNAVAILABLE`.

## Founder intervention threshold

PM proceeds without Founder interruption for reversible, bounded preview work such as code repair, tests, schemas, registry reconciliation, preview-only Railway redeployments, accessibility fixes, responsive-layout repair, route repair, security hardening, and evidence generation.

Return to Founder only when one or more of these is required:

- new consequential authority;
- new paid spend or materially expanded resource ceiling;
- new credential or confidential-source access;
- public publication or replacement of the production landing page;
- merge to `main` where it changes the public site materially;
- disclosure of unreleased ANANS implementation or trade-secret content;
- production billing/payment or real customer commitment;
- external communication that is not already explicitly authorized;
- destructive/irreversible provider action;
- strategic fork with materially different project direction;
- canonical-state ambiguity that available evidence cannot reconcile.

## Founder decision forms

Use one of three explicit terminals when PM returns an authority decision:

- `EXECUTE` — grant bounded authority to the exact packet, permitted effects, resource ceiling, and stop conditions.
- `HOLD` — preserve current state; do not execute the proposed effect.
- `REJECT` — do not retain the proposed candidate/route.

Do not use vague approval as authority for merge, publication, external send, spend, production mutation, or confidential disclosure.

## Daily Founder review

1. Read the PM terminal/status packet rather than the raw execution transcript.
2. Identify the active bottleneck: technical, evidential, resource, external-party, authority, or strategic.
3. If technical and already in scope, send it back to PM for bounded repair; do not micromanage the patch.
4. If evidential, require the missing test, assay, receipt, or external observation.
5. If authority-bound, issue `EXECUTE`, `HOLD`, or `REJECT` against the exact object.
6. If strategic, require RevLane plus Track X before allocating another major sprint.
7. Require canonical-state reconciliation after each material milestone.

## Required PM report shape

Every material terminal must state:

- current implementation state;
- controlling evidence;
- missing primitive;
- failure frontier;
- authority boundary;
- sharpest lawful next action;
- exact branch/commit/deployment state;
- tests and receipts;
- AEL retain/reject results where applicable;
- RevLane corrections;
- Track X saturation result;
- explicit non-claims.

## Build priority order

1. Canonical Village semantic registry.
2. Reconcile each building with existing ANANS/public-site primitives; avoid duplicate machinery.
3. Backend-binding registry with truthful implementation states.
4. Role/authority projection into the interface.
5. Receipt/status projection.
6. Functional building routes and read-only/live backend tests.
7. Admin/guest lifecycle and hostile auth tests.
8. Approved 1536×1024 visual fidelity and responsive delivery.
9. AEL usability/comprehension candidate assays.
10. Final RevLane/Track X reconciliation.
11. Founder public-release decision.

Do not invert this order into repeated cosmetic polishing while semantic/backend bindings remain incomplete.

## AEL rule

AEL may generate and compare candidates but retains only demonstrated improvements with no material governance, security, evidence, accessibility, or route regression. Evaluator preference alone is not user evidence or causal proof.

## RevLane rule

Run RevLane before any material state promotion and after registry, backend-binding, auth, visual, AEL, and integration milestones. RevLane must identify category errors, unsupported claims, duplication, stale bindings, authority leakage, state misclassification, substitution risk, and failure conditions.

## Track X rule

Track X searches for the highest-leverage lawful improvement. Before adding a new component it must test whether an equivalent primitive, route, schema, adapter, test, or protocol already exists. Prefer `extend / reconcile / reuse / retire` over parallel reinvention.

## Stop conditions

Fail closed and stop for Founder/external authority when resolution requires new spend, secrets, public release, production effects, destructive mutation, legal/customer commitment, external witness/buyer action, or disclosure beyond the current boundary.

Do not stop at the first ordinary technical failure. Capture failure, diagnose, make the smallest in-scope repair, rerun the failing test, run regression, and retain the repair only if green.

## Public/non-public distinction

The current restricted preview authentication limits access to the runnable Railway preview. It does not make material stored in this public GitHub repository confidential. Do not represent repository-resident preview source/artwork as trade-secret custody.

## Completion criterion

The ANANS Village build is not complete because a page renders. Completion requires a canonical registry, truthful primitive/backend bindings, role/authority enforcement, working routes, receipt/status projection, hardened guest/admin separation, responsive high-fidelity visual delivery, AEL receipts, final RevLane with no unresolved in-scope P0/P1 defects, Track X saturation, healthy restricted deployment, and a verifiable evidence packet.

Public promotion remains a separate Founder decision.
