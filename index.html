Admission control for AI agents

Every agent action leaves a receipt.Including the ones that were refused.

ANANS decides, before an agent executes, what it is allowed to touch — and produces evidence afterwards that a reviewer who was never present can check offline, on their own machine, without trusting us.

01 / PROBLEM

Building got fast. Approving didn't.

Coding agents can now produce in an afternoon what used to take a quarter. Everything downstream of production became the constraint: review, sign-off, compliance, and the question nobody can answer cleanly — what exactly did it do while nobody was watching?

The common answer is a log. A log is written by the thing being audited, and it can only be read by someone who already trusts the system that wrote it. When a regulator, a client, or your own security team asks for proof that an agent stayed inside its authority, a log is an assertion, not evidence.

The gap isn't capability. It's that nothing in the stack was built to be checked by a stranger.

02 / APPROACH

Decide before. Bound during. Prove after.

Three properties, in that order. The order is the design: nothing downstream can repair a decision that was never made.

  • Decide before execution

    An agent receives a task bound to an authority that already existed — exact action, allowed paths, resource ceiling, and an expiry. Authority is granted by policy or by a person, never assembled by the agent from its own confidence. Absent or ambiguous authority is a refusal, not a warning.

  • Bound the effect

    Agreement among reviewers, ensembles, or planning loops can change what is known. It cannot change what is permitted. A component that evaluates whether a condition is met must not also be able to widen the condition, extend its own window, or approve its own output.

  • Produce checkable evidence

    Every decision, admission, effect, and refusal writes a receipt into a hash-linked record. The record ships with an offline verifier. Someone who was not present, and who has no access to the running system, can determine what the run supports — and, just as importantly, what it does not.

Walkthrough: the build room, cold

Non-actuating demonstration

    01Entry

    The first thing the cockpit tells you is what it cannot do. Before any capability is shown, every disabled surface is named.

    ANANS GOVERNED BUILD ROOM

MODE                 NON-ACTUATING DEMONSTRATION
LIVE EXECUTION       DISABLED
WORKER DISPATCH      DISABLED
SOURCE MUTATION      DISABLED
RUNTIME GUARD        ATTESTED LOCALLY / SOURCE UNCOMMISSIONED
PRODUCTION           WITHHELD

    You should know within five seconds that this is not a live autonomous-agent demo. If a governance product hides that, nothing after it is trustworthy.

    02The objective

    Work starts from a bound artifact, not a prompt in someone's history. You can see which file supplied it and check its hash.

    OBJECTIVE

Create a JSON artifact containing:
  { "environment": "synthetic", "status": "ready" }
Then verify it contains those exact values.

SOURCE       synthetic_demo_objective.json
STATE        BOUND
SHA-256      3e21e665f5…d92aa535
AUTHORITY    SYNTHETIC DEMONSTRATION ONLY

    An objective describes desired work. On its own it authorises nothing.

    03Authority

    Separate from the objective: what this run is permitted to do. Written before execution, not derived from it.

    AUTHORISED
  execute two declared block types
  write only beneath the run directory
  verify the generated JSON
  emit receipts

NOT AUTHORISED
  shell or subprocess
  dynamic import
  repository access
  source mutation
  network or browser
  spawning further workers
  merge or promotion

USE          SINGLE-USE
REPLAY       PROHIBITED
EXPIRY       AT TERMINAL

    “Can it just decide to do more?” No. The graph contains only declared block types; unknown capabilities are rejected rather than interpreted.

    04Work graph

    The whole of what this agent can do, shown as a graph. There is no general coding agent behind it.

    BLOCK_A   EMIT_JSON
   │  out    synthetic_output.json
   │  path   synthetic_demo/output/
   │  ends   BLOCK_A_PASS | BLOCK_A_REFUSED
   ▼
BLOCK_B   ASSERT_JSON
      in     synthetic_output.json
      checks environment=synthetic status=ready
      ends   BLOCK_B_PASS | BLOCK_B_ASSERTION_FAILURE

EXECUTOR EXPOSES:  EMIT_JSON, ASSERT_JSON

    Two verbs. That is the entire surface. Narrowness here is the point, not a limitation of the demo.

    05Budget

    Ceilings are declared before the run and are terminal conditions rather than warnings.

    This budget is a declaration bound to a synthetic packet. It is not evidence that an uncommissioned live guard enforces production budgets. The cockpit says so on the panel itself.

    07Replay denied

    The same invocation with the same authorisation, attempted twice. Single-use means single-use.

    REQUEST            same invocation, same authorisation
RESULT             REPLAY_DENIED
FILESYSTEM DELTA   none
MANIFEST BEFORE    identical
MANIFEST AFTER     identical

EVIDENCE TYPE      FROZEN LOCAL RESULT
NOT                INDEPENDENT EXTERNAL REPRODUCTION

    “How do I know it didn't write again?” The before and after manifests are both shown. No hash and no size changed.

    08Refusal

    A request arrives without a declared receipt contract. This is the case that matters most.

    REQUEST            execute declared graph
RECEIPT CONTRACT   MISSING

DECISION           DENY_FAIL_CLOSED
EXECUTION ENTERED  no
OUTPUTS CREATED    0

REASON             REQUIRED EXECUTION EVIDENCE NOT DECLARED

    A refused request produces an inspectable state, not silence. Systems that fail quietly are the ones you cannot audit later.

    09Adverse evidence

    Historical findings and current blockers are shown next to the successful run, not filed away from it.

    RUNTIME GUARD — HISTORICAL
  hostile chain, earlier candidate   5 passed / 10 failed
  classification                     NECESSARY_BUT_DEFECTIVE
  current source state               UNCOMMISSIONED
  live use                           PROHIBITED

OWNER IDENTITY EXPORT
  authority                          present
  execution                          not entered
  reason                             eligible owner identity inactive

    Why show failures to a visitor? Because a record with the failures removed cannot be relied on for the parts that remain.

    10Admission state

    Four separate questions, four separate answers. They are never collapsed into one green light.

    SYNTHETIC EXECUTOR
  local result          PASS
  production admission  WITHHELD
  external validation   NOT PERFORMED

RUNTIME GUARD
  repair                ATTESTED LOCALLY
  authoritative source  UNCOMMISSIONED
  live execution        PROHIBITED
  next gate             OWNER IDENTITY SOURCE EXPORT

    A single status light is a claim that four independent questions have the same answer. They rarely do.

    11Forbidden action

    The visitor presses a clearly marked control that asks for live worker dispatch.

    REQUEST            LIVE WORKER DISPATCH

RESULT             REJECTED
  LIVE_EXECUTION_DISABLED
  WORKER_DISPATCH_DISABLED
  RUNTIMEGUARD_COMMISSIONING_NOT_ASSUMED

EXTERNAL ACTION    none
RECEIPT            issued for the refusal

    Even a forbidden action produces evidence. A greyed-out button tells you nothing; a receipted refusal tells you the boundary was reached and held.

    12What you should conclude

    The walkthrough succeeds only if you leave with an accurate picture — which is narrower than a demo usually wants to give you.

    A real governed control and evidence layer exists locally.
Its live execution boundary is deliberately disconnected.

You should be able to answer:
  what was requested
  what authority existed
  what was permitted
  what actually happened
  what evidence supports it
  what failed or remains blocked
  why promotion was withheld
  what must happen before live execution

You should not conclude:
  that this is production-ready
  that agents can touch real repositories today
  that any external validation exists

    The walkthrough fails if you leave thinking “nothing real exists” or “this is already autonomous.” The truth sits between those, and it is checkable.

    03 / STATE Mixed · read the column

    Where this actually stands

    Four different states, kept apart on purpose. A specification is not an implementation, an implementation is not a validation, and a validation on our own machines is not external proof.

    ComponentStateWhat that means
    Admission control & authority bindingBuilt · validated locallyExpiry, scope, and path enforcement with passing test suites on our hardware.
    Receipt spine & offline verifierBuilt · publishedA signed evidence bundle and a portable verifier are public. Anyone can run them.
    Bounded execution lifecycleBuilt · frozen referenceA complete governed run, hash-bound and reproducible against its own frozen source.
    Build-room cockpitBuilt · non-actuatingDisplays authority, evidence, and refusals. Deliberately not wired to live execution.
    Live agent dispatchWithheldThe runtime guard's authoritative source has not been commissioned. Not available.
    Governed component registrySpecified · not builtDesigned and catalogued. No implementation claim is made.
    Independent external validationNot performedNo third party has audited the system.
    04 / NON-CLAIMS Stated, not buried

    What this page does not claim

    A system whose entire premise is disclosing its own limits has to start with its own. If any of the following is later true, it will be said here in the same size type.

    • ANANS is not production-ready and is not for sale as a running service.
    • No agent can currently modify a customer repository through ANANS.
    • No independent party has audited the architecture, the source, or the claims.
    • The public proof bundle covers one bounded run. It does not establish that every execution path is non-bypassable.
    • Local validation is not external reproduction, and passing our own tests is not evidence about anyone else's environment.
    • No commercial demand for this has been demonstrated.
    • The synthetic executor is not a general coding agent. It performs two declared block types.
    05 / VERIFY Public · runnable

    Don't take any of this on trust

    The evidence bundle is public, offline-verifiable, and signed. It contains no proprietary source and no private keys. Clone it, run the verifier, and decide for yourself what it does and doesn't prove.

    git clone https://github.com/Anans-AI/anans-containment-proofs
cd anans-containment-proofs/proofs/nist-ma12/v0.1.0-audit

python3 -m pip install pynacl
python3 EVIDENCE/VERIFY.py --evidence_dir EVIDENCE

# Windows (PowerShell or Command Prompt):
py -m pip install pynacl
py EVIDENCE\VERIFY.py --evidence_dir EVIDENCE

# expected: VERIFY PASS

    A passing result is bounded. It tells you the recorded run is internally consistent and independently inspectable. It does not tell you who controlled the signing key, whether the harness was complete, or whether every relevant path was tested. Those remain open, and the bundle says so.
